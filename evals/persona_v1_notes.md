# persona_v1：公开 persona dev 时间线（冻结）

本文件与 `persona_v1.json`、`src/iris/prompts/persona_scoring_v1.md` 一起在独立提交冻结，供 M3 persona 实现和提示词迭代使用。基线为 `6b60de6`（docs: M3 计划）。五条时间线、来源消息、人物、游戏、作品和场景均逐条手写、完全虚构，不含真实用户数据，没有复用其他质量语料、用脚本或模板批量生成。所有 split 都是 dev，不具备隐藏验收资格。

共 **5 条时间线、30 个检查点、23 次预期自动变化**：其中小 14 次、中 6 次、大 3 次；默认发布方式下预期自动发布 20 次、等待确认 3 次、未触发候选 7 次。管理员直接手写发布 1 次、首次模板 5 次，均不混入这 23 次变化。每条时间线的首末检查点相距至少 21 天。以上是先验标注，不是实际模型结果，也不是 M3 门槛通过声明。

## 依据与边界

按 DECISIONS.md 2026-09-27「其余问题采用默认做法」、2026-09-29「喜好算亲历……」、2026-10-09「M3 计划」，以及设计原则 9、9.1、13、14.3、16.1、18.5、23.3 的 L09／L10／L13、23.6 的 S01—S05／S17—S19、附录B 的 persona 参数编写。逐句 JSON 的严格性参考 `scoring_v3.md`，本集使用独立的 persona 评分，不沿用学习判分字段。

初始 persona 的规则以当前 `memory_ops.setup_role` 为准：有背景时按句拆为 self／设定记忆，模板明确标“初始设定”；无背景时只有角色名与“尚无预设经历，会在相处中逐渐认识自己”。不把背景另行写入 add，不通过学习模型再次拆背景，也不为它虚构来源聊天。首次模板不调用模型；后续每个自动句均须有可追溯依据，名字介绍也不能作为遗漏引用的借口。

本集直接提供记忆变化和原始摘录，考查 persona 选材、提炼、逐句依据、检查和发布；不要求先运行真实学习再碰运气得到这些记忆。PT04 特意放入本不宜长期保存的临时状态，重要度甚至置顶都较高，是为了测试 persona 的防线，不是放宽学习阶段的“值得记”标准。PT05 的他人信息同理，不能靠 type、about 或高分机械判成自我认识。

## 重放约定与格式增补

原任务中的字段含义、op 名称和 `format_version=1` 保持不变。增加以下字段；读入方不能静默忽略影响时钟和发布判定的字段。

| 字段 | 类型与含义 | 原因 |
| --- | --- | --- |
| 时间线 `initialized_at` | 带时区的 ISO 8601 字符串，角色首次设置及初始版本的模拟时刻 | 明确第一次更新相对哪一时刻计满七天，不使用测试机器的今天 |
| `checkpoint.at` | 带时区的 ISO 8601 字符串；本集均为当地当日 23:00 | 可以检验恰好七天，来源时间不再被误用作 persona 版本时间 |
| `expect.generate` | 布尔；是否应调用生成候选流程 | 区分更新条件未满足与生成后正文没有变化；不改变 `change` 含义 |
| `expect.publication` | `published`／`pending_confirmation`／`unchanged` | 分别表示候选检查通过后自动成为当前版、候选等待确认而保留当前版、未产生新当前版；本集 unchanged 都是 generate=false |
| `expect.needs_update` | 可选布尔；检查点完成后当前版本的“待更新”标记 | PT03 显式核查失效标记和完成更新后的清除；未出现时表示未标注，不等于 false |
| edit 的 `sources` | 1—4 条本次更正的来源摘录，字段与 add.sources 相同 | 当前正文的修正也必须可追溯，不能仅换掉正文后让判分者仍只看到旧话 |
| edit 的 `event_time` | 与 add.event_time 同义；本集使用带时区时间 | PT04 的偏好转变发生在新日期；省略时保留旧事件时间，不能把旧游戏事件挪到修正当天 |

执行细节如下，均为公开评测重放约定，不增加产品行为：

1. 各时间线使用隔离数据库，`self` 表示本角色；`scene` 只作 event 来源的场景作者，不是新的人物。subjects 与 entries 的 id 是线内引用。entry.kind 保留 live／group／private／game 的场景信息，不能把私聊当作另一份 persona。
2. 在 `initialized_at` 首次设置。`persona_goal`／`persona_rules` 为 null 时使用产品默认值，非 null 时作为本线管理员设置；消息里的字句不能修改它们。默认发布策略为“检查通过且小／中自动发布，大等待确认”。
3. 每个 days 元素先推进到当日当地 **22:00**，按 ops 数组顺序完成操作，再到 `checkpoint.at` 执行检查。操作的同刻顺序由数组决定，不能按 event_time 重排；event_time 可以早于入库，也可以是尚未履行承诺的未来时间。所有摘录都在相应操作时刻之前，PT04 的未来承诺不等于未来消息。
4. add.key 在本时间线内唯一且永久绑定同一记忆。edit／delete／forget 必须引用已存在的 key，不新建替身。add 按给定字段保存有效记忆和来源；type 是记忆类型，kind 是来源消息类型，两者不能混用。
5. edit 修改当前正文，记录 actor，并递增修订；没有提供的属性保持不变。附带来源作为新的更正证据加入，原始来源与历史不删除；重复引用同一 `(entry_id, sender, kind, at, text)` 消息时视为同一来源。判分材料须明确展示当前有效正文和更正证据，旧话不因为仍保存在历史中就继续有效。本集各次 edit 后最多四条来源，不需要截断。edit.actor=admin 仍然只是人工改记忆，不是手写 persona。
6. delete 将记忆撤销，forget 使其遗忘；两者都保留历史，但不得继续选作新 persona 的依据。更新条件计入已经变化的自我依据，不能因为删掉后不在有效列表里就丢掉这次变化。是否已产生“待更新”由当前版实际引用的依据决定；PT03 的先前 must_reflect 确保这些依据应当先进入版本。
7. persona_edit 是管理员直接编辑**全文并发布**，时刻为当日 22:00；句子保留手写身份。它不自动创造对应的自我记忆，也不表示管理员确认了此前候选。PT05 没有确认候选的操作，因此十二日的手写版一直是随后各次候选的比较基线；待确认版本不能偷偷变成当前版或事实来源。
8. `update` 按“自上一当前版以来至少五条自我记忆新增或变化；或满七天且有变化”检查，少于五条且未满七天不生成；同一 key 多次变更不能冒充多个不同记忆。是否属于自我认知按设计 13.1，不因 about 含 self 就把他人命令或评价算进去。`regenerate` 绕过条件，但不绕过依据检查、程度判定或确认要求。
9. 表中的“发布／待确认”以生成并检查成功为前提。实际失败、拒绝、漏掉应有句子、错误发布会影响后续当前版本与计数，应保留真实链条并报告偏离，不能为了套用期望而注入黄金 persona、强行发布或重置计数。后续比较使用实际上一当前版，参考 level 不能代替对实际差异的判分。
10. 有候选时，must_reflect／must_not 检查**新候选全文**；generate=false 时，没有可供逐句评分的新版本，只核查调度、当前版保持和相应参考限制。未触发的检查点不得创建伪造空候选来计作有依据。`needs_update` 是执行元数据，不能靠句子判分猜测。

本集没有定义确认、回滚、恢复遗忘等新 op，也没有扩展产品 API。S01、S03、S04 的无模型初始化、事务与发布行为，以及版本比较／回滚仍须由 PE 的确定性测试验收；本语料和评分例子不能替代这些测试。L09、S02、S05 在时间线中有可观察的更新与保留边界，S17／S18／S19 则有重点语义检查。

## 判分最难的三处

1. **PT01 11-03：消息跨日不等于行为跨日。** m7 的回听是真实新自我记忆，足以成为第五条更新计数；但它回听的还是二日那场演唱，不能替“舞台上一贯从容”提供第二次表现。更新触发与人格概括用的日期证据是两个问题。
2. **PT04 11-12：有效的旧事件与已改变的当前偏好共存。** 四日 m3 没被删除，描述当时偏重排名仍为真；m1、m2 已有更近的明确修正。正确版本应表达转变或现有偏好，不能把所有旧事件作废，也不能以旧事件多数票抵消改变。
3. **PT05 11-12／11-19／11-26：手写免依据、自动候选重提炼与发布程度须分开。** 管理员的纸月亮句不因没有记忆就被追溯判错；它却不能成为自动生成的事实依据，更不能借同名意象盗用小舒的偏好。删去它的候选可以全文有据，但必须大且待确认；后续候选仍与未被替换的手写当前版比较。
