## 参数与兼容性

新数据库的独立纯全文默认：`fallback_tokenizer=jieba`、`fallback_lexical_min=0.0`、`fallback_lexical_max_df=0`。覆盖率 0 仍要求至少一个 FTS 词项命中；0 文档频率表示关闭长片段豁免。未配置 embedding、模型／维度未标定、调用失败或两秒超时都使用这组设置。下一次 embedding 成功时恢复混合参数。

混合参数仍为第五轮的 trigram、覆盖率 0.75、长片段最大文档频率 2、向量绝对下限 0.35、相对比例 0.75、权重 1、2048 维 float32、原问题前缀。已有数据库设置不改写；缺少独立字段时从原共享字段解释。显式构造参数仍可用于受控方案比较，显式 fallback 参数优先。学习检索不使用这些新字段。

先添加独立测试文件，旧实现上 9 failed／2 passed；随后实现。两项已有覆盖率测试显式固定 0.75，继续检查原门槛逻辑，避免把可标定默认值当成固定契约。新增测试全部位于 `tests/test_retrieval_fallback.py`。

## 性能三次复测

初次按原点名实现跑了完整三轮，5 万条点名 prepare P95 为 433.6／383.6／543.3ms。每轮开始时均没有其他测试，但第二、三轮中途分别出现其他会话的 Python 3.13／3.12 测试（进程观察 21／22 次）；这两轮不用于验收，原始数据及负载保留在 baseline-1／2／3。第三轮有 R10 超限，不能把波动解释为通过。

第一步省掉排名时重复的 memories JOIN 并增加姓名预筛，三次点名 P95 为 379.0／765.3／690.7ms，后两次无并发测试仍失败；原始结果在 optimized-1／2／3。不点名和向量耗时也同时增加，提示存在机器波动，但不能据此判通过。

最终实现将同一精确锚点条件前移到 FTS 排序之前：当前查询的只读连接注册确定性 SQLite 函数，直接人物关联一次读取，正文先检查任一锚点标签，再由原完整姓名规则校验；结果在本次查询内按 ID 缓存，供两个全文通道、向量和人物要点共用。函数只处理 FTS 匹配行，原生命周期／结构条件仍在 LIMIT 之前，BM25 使用同一整库统计，候选上限与排序规则不变。没有增加索引、迁移或跨查询缓存。

诊断剖析（各 5 次热身、5 次采样，不是 R10 测量）：SQLite execute 每次 153 → 45 次，lexical_lane 累计耗时 317.0 → 75.3ms，带剖析的 prepare 平均约 386.3 → 131.5ms。完整姓名匹配最终每次约 5,002 次，较第一步 2,002 次更多，因为排序前检查全部全文命中，但不再逐批查库或给其他人的记忆排序。剖析含额外开销与负载差异，仅作定位。[最初剖析](profile-before.json)、[第一步](profile-after.json)、[最终](profile-final.json)。
