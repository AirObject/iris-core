# 代码规范：实现自描述与文档边界

> 本文件是现行代码规范的唯一维护正文；冻结原始版本仅供设计和审核参考，见[文档关系](INDEX.md)。本次迁移保留全部规范条款。

## 适用范围

本规范适用于本项目维护的生产代码、测试代码、脚本、迁移代码、配置定义、运行时模板以及参与实现的生成代码，覆盖文件名、目录名、标识符、注释、docstring、日志、异常信息、测试描述和资源说明。

本文规定实现的表达方式和审查要求，不替代业务设计，也不将文档中的规划结构转换为运行时结构。文中“必须”和“禁止”为合并前要求，“建议”为允许说明理由后调整的做法。示例用于说明规范，不代表仓库已经存在对应实现。

## 核心原则

**文档指导设计，代码表达实现。实现必须使用业务语义和技术语义，不携带文档编号、开发阶段或对话过程。**

单独打开一个文件时，读者应能从名称、类型和注释中理解它的职责、关键规则和边界，而不必先寻找设计文档、实施计划或历史聊天。

需要跨文件引用时，只引用实际存在的代码文件或代码符号，并在当前文件说明引用的用途。引用用于帮助定位实现，不代替本地说明。

## 禁止将规划信息写入实现

### 禁止的内容

实现中不得出现以下信息作为名称、解释依据或执行条件：

| 内容 | 不合规形式示例 | 要求 |
| --- | --- | --- |
| 模块或基础设施编号 | `M13Provider`、`I02Client` | 使用 `ProviderService`、`ModelClient` 等职责名称。 |
| 事务、验收或决定编号 | `apply_T03`、`test_V07`、`D04_policy` | 使用操作、行为和预期结果命名。 |
| 开发阶段或批次计划 | `phase_two_handler`、`stage_three_only` | 使用真实业务能力命名，不以交付进度组织实现。 |
| 文档章节或方案引用 | “按设计第六节处理”“实现模块表中的某项” | 直接说明本地执行的规则和理由。 |
| 对话与修改过程 | “根据上一轮决定”“这次新增”“此前已确认” | 描述当前有效行为，不记录讨论过程。 |
| 临时实施过程 | “本阶段先这样”“下个阶段补全” | 明确当前能力边界及实际失败行为。 |
| 外部编号化概念的机械复制 | `s1_messages`、`s2_messages`、`s3_messages` | 使用 `recent_context_messages`、`target_messages`、`history_context_messages` 等角色名称。 |

禁止范围不只限于注释。不得将这些规划信息写入配置键、数据库列名、API 字段、日志事件、异常字符串、测试名称、文件路径或运行时 prompt。

使用语义化错误码、事件名、版本号和对象标识不违反本规范。例如，`DREAMING` 表达运行模式，`batch_id` 标识实际批次，`config_revision` 表达配置版本；它们不是设计文档编号。

### 不应误伤真实业务信息

禁止的是开发规划的阶段和编号，不是系统本身需要表达的顺序、状态和数值。

HTTP 状态码、协议版本、数据库迁移版本、模型名称、标准日志等级、真实任务标识和业务数值可以保留。梦境进入、运行、回流、故障等实际状态也可以明确建模，但必须使用有意义的状态名称，不能以“第一阶段、第二阶段”代替语义。

历史兼容格式必须转换为内部语义化类型时，可在协议边界保留对方真实要求的字段名；不能以兼容为由保留本项目自己创造的规划编号。

## 命名与目录

目录和文件按业务职责或技术职责组织，不按开发顺序、里程碑、文档章节或验收清单编号组织。

| 不合规命名 | 语义化命名示例 |
| --- | --- |
| `modules/m13_provider.py` | `modules/provider/service.py` |
| `phase_one_buffers.py` | `buffers/batch_queue.py` |
| `apply_t03()` | `commit_learning_result()` |
| `test_a75()` | `test_failed_batch_preserves_history_context()` |
| `config_p04` | `goal_deduplication_policy` |
| `s2_snapshot` | `target_snapshot` |

类、函数、变量、配置项和事件名应表达对象、动作、结果或约束。不要使用需要查阅外部映射才能理解的编号简称。

允许使用稳定、业内常见且在上下文中明确的技术缩写。含义不直观的领域术语，应在所属文件首次使用时解释。不得因为某个编号在设计文档中有解释，就认为它在源码中已经自解释。

## 每个文件的独立可读性

### 文件级说明

本项目维护的源码文件应有简短的模块级说明。Python 使用模块 docstring；其他语言使用其对应的文件级说明方式。说明的位置遵守语言及许可证要求。

文件级说明至少回答：这个文件负责什么、围绕什么数据或行为工作，以及最重要的边界是什么。包含状态转换、持久化、副作用或恢复逻辑时，还应说明相关约束。

说明的长度与文件复杂度相匹配。简单的导出文件可以只说明公开范围，不需要机械重复整份架构；复杂的队列、事务或 Provider 文件则必须解释关键不变量。

合规示例：

```python
"""管理单个入口的缓存批次与轮转。

批次只消费冻结时记录的目标消息，处理期间新到达的消息保留在待处理区。
普通学习失败时保留目标消息的末尾，供下一轮作为历史上下文使用。
明确因敏感信息拒学时不保留该尾部，并清空本入口的历史辅助槽位。

本模块不调用模型，也不负责生成正式记忆。
"""
```

不合规说明包括：“队列模块”“这里实现某项设计”“规则见文档”“与其他模块相同”。这些表达不足以让读者理解本文件。

### 独立可读不等于复制全部代码

文件仍可以使用正常的导入和模块协作，不要求把被调用实现复制进来。

当前文件需要说明自己为什么调用某能力、期待什么输入输出和错误，以及自身承担哪些保证。被调用能力的内部算法由其所在文件说明。

不要为了让文件独立可读，把同一段长规则复制到所有文件。共享规则应通过类型、函数和验证器集中实现，各调用文件解释与自身有关的部分。

## 注释与 docstring

### 表达要求

注释必须表达完整含义，清楚说明对象、条件和行为。禁止只有零散编号、无上下文的半句话、仅作者自己能理解的暗示，或以“按上文”“按之前讨论”替代说明。

注释应描述当前实现，不叙述开发历史，不使用“AI 要求”“为了通过某项验收”等理由解释业务行为。

有价值的注释重点说明：为什么这样处理、必须保持什么不变量、允许什么失败，以及为什么不能采用看似更简单的做法。

不要为显然的赋值或普通控制流重复注释。注释完整性不要求每行都有注释，也不要求注释越长越好。

合规示例：

```python
# 只移除批次冻结时记录的目标消息，避免误删模型调用期间新到达的输入。
# 留下的尾部仅用于解释下一轮目标，不会将本轮失败消息重新加入待总结范围。
```

### 公共接口说明

公开类、函数和模块间端口应有与其复杂度相称的 docstring，明确说明：

| 项目 | 应包含的内容 |
| --- | --- |
| 职责 | 操作做什么，以及调用后能够期待什么。 |
| 输入 | 重要参数含义、单位、范围、可空条件和必要前置条件。 |
| 输出 | 返回内容、状态含义，以及空结果与失败的区别。 |
| 副作用 | 是否修改持久化状态、调用外部 API、发布文件或改变队列。 |
| 失败 | 可预期的错误、是否保留输入，以及调用方如何识别结果未知。 |
| 重复调用 | 有副作用时说明幂等键、重复执行与本地重试边界。 |

类型注解已经清晰表达的信息不必机械重复；事务、时限、引用所有权和远程副作用等不能从类型直接看出的行为必须说明。

复杂内部函数也要解释关键逻辑。简单私有辅助函数可以主要依赖语义化名称和类型，但不能以“私有”为由省略重要限制。

## 引用规范

### 允许的引用

需要帮助读者定位相关实现时，引用真实存在的仓库相对代码路径、模块、类或函数。引用必须同时说明它与当前逻辑的关系。

路径和符号应与当前代码一致；移动文件或重命名符号时同步检查引用。建议避免依赖易变化的行号。

即使已经给出代码引用，当前注释仍须解释本地规则。例如，不能只写“见其他文件”，而应先说明当前操作由谁完成、当前文件不做什么，再给出定位信息。

### 禁止的引用

源码、注释、docstring、测试说明和运行时模板不得引用设计文档路径、章节、表格、ADR 编号、验收编号、实施计划或历史对话，作为理解实现所必需的信息。

不得用“文档已经解释过”替代代码说明。代码中的固定业务行为必须通过命名、类型、约束和注释直接表达。

需求与实现的追踪关系可以保留在文档、开发任务和代码审查记录中。它的方向是由文档定位代码，不要求代码反向依赖文档编号。

许可证及必须保留的版权声明按其要求保留，不得为消除引用而删除法定或授权所需信息。此例外不适用于普通设计说明。

## 文档与运行时的边界

### 文档不参与运行时决策

应用不得在运行时读取规划文档，以判断应该使用哪个模块、当前实现到哪个开发阶段、如何执行某条验收要求，或如何解释编号。

禁止将设计文档直接作为内部 agent 的隐藏运行规则，也禁止通过拼接整份规划材料，让模型自行推导本应明确实现的权限和状态机。

已确定行为应落实为类型、接口、状态机、配置定义、验证器、具体实现和测试。prompt 可以说明认知任务，但不能代替确定性的权限、事务和生命周期规则。

### 运行资源与设计文档不同

正式运行所需的 prompt 模板、配置 schema、语言资源和协议 schema 可以独立保存为资源文件。它们属于实现的一部分，同样必须使用语义化名称、明确版本和可验证内容，不得夹带规划编号、章节引用或开发阶段说明。

文件扩展名不是判断标准。Markdown 格式的 prompt 也可以是运行资源，但不能因此把设计报告当作可执行规则加载；反之，JSON 或 YAML 中出现的规划说明也不因格式不同而获准进入实现。

源码生成模板也必须遵守规范，不能在生成文件中自动写入“对应某模块编号”或“按照某设计章节生成”的说明。

## 测试、日志与错误信息

### 测试

测试文件和测试函数按被验证的行为命名，不使用需求、决定、阶段或验收编号。

测试自身必须交代必要的初始状态、操作和预期结果。读者不查文档，也应理解该用例为什么成功或失败。

断言表达业务含义，例如“普通失败仍保留历史上下文”，而不是“满足某项验收”。测试数据中的主体、入口和对象 ID 可以使用明确的示例值，但不能用规划编号代替被测语义。

测试与需求的映射留在文档或测试管理记录中，不反向写入测试实现。

### 日志与错误

日志使用标准等级和语义化事件名，记录实际运行状态、对象、操作和原因。不输出开发阶段完成情况，也不以文档编号说明故障。

允许记录真实的请求 ID、批次 ID、配置版本、Provider 尝试 ID 和错误码。这些用于定位运行事实，不属于规划标识。

异常信息应说明什么操作失败、已知原因、哪些效果已发生或尚未确认。不得只给出一个只有查文档才知道含义的内部编号。

日志和异常中的文字同样要具有完整含义；结构化字段可以简洁，不必将每个字段值写成句子。

## 配置、常量与模块协作

所有可调参数通过统一配置模块注册和获取。禁止在不同文件中重复声明私设默认值，也禁止通过环境变量或局部配置副本绕过统一管理。

配置名称表达实际用途，定义中说明单位、合法范围、默认值、生效边界和权限。注释直接解释参数作用，不以某项设计编号代替含义。

不可变业务规则使用有名称的常量、枚举、类型或验证器表达，不为了消除魔法变量而把核心正确性做成可关闭开关。

调用 Provider、日志、配置或其他模块时，应使用公开端口。不得通过直接请求模型端点、全局可变配置、任意 SQL 或文件读取绕过已有边界。说明这些限制时，应讲清当前文件的责任，不引用模块编号。

配置快照、对象修订和事务操作标识属于运行机制，可正常表达；它们不应被混同为被禁止的文档版本或开发阶段。

## 未完成能力与维护

不得以“后续阶段实现”作为成功返回、空实现或静默降级的理由。尚不支持的能力应有明确的能力声明或错误结果，避免调用方误以为已经完成。

确需保留待办注释时，应完整说明当前限制、触发条件和预期修正方向，不包含规划阶段、文档编号或对话引用。仅写 `TODO`、`FIXME`、`pass` 的含糊占位不能替代接口契约；语言结构合法的空体本身不被一概禁止，但公开行为不能靠空体伪装完成。

修改行为时同步修改名称、类型、docstring、注释、日志语义和测试。发现注释与实现冲突时，必须查明正确行为并一起修复，不能只改注释掩盖缺陷。

## 检查与合并门槛

### 自动检查

建议在仓库检查流程中覆盖以下事项：

| 检查 | 预期结果 |
| --- | --- |
| 文件、标识符与字符串扫描 | 识别规划编号、开发阶段名称、文档路径和章节式引用。 |
| 注释与 docstring 检查 | 本项目源码具有适当的模块说明，公共接口的说明不依赖外部设计材料。 |
| 架构约束检查 | 运行代码不读取规划文档，模型调用不绕过 Provider，配置不分散读取。 |
| 引用有效性检查 | 注释中的代码路径和关键符号可定位，重命名后没有失效引用。 |
| 生成代码检查 | 模板及生成产物不自动注入文档编号或阶段标记。 |

文本扫描只能发现候选问题，不能单靠“出现字母加数字”就判定违规。必须区分规划编号与真实模型名称、协议版本、业务 ID、状态码和迁移编号。

所有自动排除规则应范围明确，不允许通过全目录忽略规避本项目实现代码的检查。

### 人工审查

合并前应能够直接回答：单独打开每个变更文件，是否能看懂职责、关键行为和边界？公共接口是否说明实际副作用与失败？引用是否指向真实代码且不是本地说明的替代品？文件是否夹带实施过程、规划编号或对话历史？

任何“必须回去翻设计文档才能知道这段代码在做什么”的情况，都应补充语义化名称、类型或本地说明，而不是简单再加一个文档链接。

本规范不以注释数量衡量质量。最终要求是：**实现行为可直接理解，规则可在代码与测试中验证，规划痕迹不成为源码和运行时的依赖。**
